# V4 – Role-Based Authorization & Booking Ownership

## Overview

**Project:** Movie Ticket Booking System  
**Framework:** .NET 10  
**Database:** SQL Server Express  
**ORM:** Entity Framework Core  
**Authentication:** JWT Bearer Authentication

V4 extends V3 with role-based authorization and customer booking ownership. It corresponds to two Git commits:

1. `feat: implement role-based authorization for admin`
2. `feat: implement role-based authorization and booking ownership`

## 1. Roles

| Role | Intended responsibilities |
|---|---|
| Customer | Browse movies and shows, create bookings and manage own bookings |
| Admin | Manage movies, theatres, screens, seats, shows and all bookings |
| TheatreManager | Intended for theatre-specific management; ownership restrictions are not fully implemented yet |

Do not grant TheatreManager unrestricted access to all theatre resources until theatre-specific ownership checks are implemented.

## 2. Role constants

Created `Constants/UserRoles.cs`:

```csharp
namespace MovieTicketBooking.Constants;

public static class UserRoles
{
    public const string Customer = "Customer";
    public const string Admin = "Admin";
    public const string TheatreManager = "TheatreManager";
}
```

Admin-only endpoints use `[Authorize(Roles = UserRoles.Admin)]`. Endpoints accessible to either Customer or Admin use `[Authorize(Roles = UserRoles.Customer + "," + UserRoles.Admin)]`. Multiple roles in the same attribute are an OR condition.

## 3. Development account seeding

A `RoleSeeder` creates predefined Admin and TheatreManager accounts in the Development environment. It checks whether an account already exists before creating it.

In `Program.cs`:

```csharp
if (app.Environment.IsDevelopment())
{
    await RoleSeeder.SeedAsync(app.Services, app.Configuration);
}
```

### Password hashing

```csharp
builder.Services.AddScoped<IPasswordHasher<User>, PasswordHasher<User>>();
```

Seeded passwords are hashed before being saved. Plain-text passwords must never be stored in the Users table.

### User Secrets

Development seed credentials are supplied through ASP.NET Core User Secrets, not committed to `appsettings.json` or source control.

```powershell
dotnet user-secrets init
```

Set values using the exact configuration keys read by the actual `RoleSeeder.cs`. For example, if the seeder reads `SeedUsers:Admin:Password`:

```powershell
dotnet user-secrets set "SeedUsers:Admin:Password" "your-password"
```

Use the corresponding key for the TheatreManager password. Verify the exact keys in `RoleSeeder.cs` before using these examples.

User Secrets are intended for development. Production credentials must come from a secure production configuration provider. Never commit actual passwords or signing keys.

## 4. Booking ownership

V4 adds a direct relationship between Booking and User.

The `Booking` model includes:

```csharp
public int UserId { get; set; }
public User? User { get; set; }
```

Relationship:

```text
User (1) -------- (*) Booking
```

One user can have multiple bookings. Each booking must reference one user.

### Fluent API

In `ApplicationDbContext.OnModelCreating`:

```csharp
modelBuilder.Entity<Booking>()
    .HasOne(x => x.User)
    .WithMany()
    .HasForeignKey(x => x.UserId)
    .OnDelete(DeleteBehavior.Restrict);
```

`DeleteBehavior.Restrict` prevents deletion of a user while bookings reference that user.

## 5. Database migration strategy

Existing booking records were retained, so the relationship was introduced in two migrations.

### Migration 1 – AddBookingUserRelationship

The model initially used a nullable foreign key:

```csharp
public int? UserId { get; set; }
```

Commands:

```powershell
Add-Migration AddBookingUserRelationship
Update-Database
```

This added the nullable `UserId` column and foreign key.

### Backfill existing bookings

Existing booking emails were matched against user emails:

```sql
SELECT
    b.BookingId,
    b.CustomerEmail,
    b.UserId,
    u.UserId AS MatchedUserId
FROM Bookings b
LEFT JOIN Users u
    ON b.CustomerEmail = u.Email;
```

After verifying matches:

```sql
UPDATE b
SET b.UserId = u.UserId
FROM Bookings b
INNER JOIN Users u
    ON b.CustomerEmail = u.Email;
```

Records without a matching user must be handled deliberately, not assigned to an unrelated account.

### Migration 2 – MakeBookingUserIdRequired

After backfilling existing records, the model was changed to:

```csharp
public int UserId { get; set; }
```

Commands:

```powershell
Add-Migration MakeBookingUserIdRequired
Update-Database
```

The database now enforces a mandatory Booking–User relationship.

## 6. JWT claims and booking ownership

The JWT generated by `JwtService` includes:

```csharp
var claims = new[]
{
    new Claim(ClaimTypes.NameIdentifier, user.UserId.ToString()),
    new Claim(ClaimTypes.Name, user.FullName),
    new Claim(ClaimTypes.Email, user.Email),
    new Claim(ClaimTypes.Role, user.Role)
};
```

| Claim | Use |
|---|---|
| NameIdentifier | UserId for ownership |
| Name | Customer name |
| Email | Customer email |
| Role | Role authorization |

The client does not supply the identity of the user creating a booking. The backend obtains it from the validated JWT.

## 7. Booking DTO change

`CreateBookingDto` no longer accepts customer name or email. The request contains booking-specific data such as CustomerPhone, ShowId and SeatIds.

Customer name and email are obtained from JWT claims. This prevents a customer from claiming another user's identity in the booking request.

## 8. BookingService changes

### Creating a booking
The service receives the authenticated identity:

```csharp
CreateAsync(
    CreateBookingDto dto,
    int userId,
    string customerName,
    string customerEmail)
```

It assigns `UserId`, `CustomerName` and `CustomerEmail` from the authenticated user's details.

### Retrieving a booking
The service checks ownership:

```csharp
if (userId.HasValue && booking.UserId != userId.Value)
    return null;
```

A Customer is supplied with their own UserId. Admin passes `null` to bypass the ownership filter. The controller returns `404 Not Found` when a customer requests another customer's booking.

### Cancelling a booking
The service checks ownership before changing booking or seat status. A customer cannot cancel another customer's booking. Admin can cancel any booking.

## 9. Repository tracking change

Read-only retrieval uses `AsNoTracking()`. Cancellation modifies an existing booking and its associated ShowSeat records, so a separate tracked retrieval method was added.

Interface:

```csharp
Task<Booking?> GetByIdForUpdateAsync(int id);
```

Implementation:

```csharp
public Task<Booking?> GetByIdForUpdateAsync(int id)
{
    return Details()
        .FirstOrDefaultAsync(x => x.BookingId == id);
}
```

`BookingService.CancelAsync()` uses this tracked method before changing booking status, allowing `SaveChangesAsync()` to persist modifications.

## 10. Program.cs and JWT configuration

The application registers JWT bearer authentication and authorization. The request pipeline uses:

```csharp
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();
```

Authentication must run before authorization. JWT validation checks issuer, audience, token lifetime and signing key.

## 15. V4 outcome

V4 introduces role constants and role-based authorization, development seeding of privileged accounts, password hashing, User Secrets for development credentials, a mandatory Booking–User relationship, a two-stage migration and data backfill, JWT-based booking ownership, customer-specific retrieval and cancellation, Admin access to all bookings, and tracked EF Core retrieval for cancellation.

### Known limitations
- The booking transaction makes its database writes atomic, but does not by itself fully prevent two simultaneous requests from attempting to book the same seat. Concurrency protection remains a separate improvement.
- TheatreManager theatre-specific ownership restrictions are not fully implemented in V4.
